Documentation

Hydra has three surfaces, a CLI, an interactive TUI cockpit, and a desktop app: sitting in front of every AI model on your machine. This covers all three, the tools it plugs into, and every command: what it does, how it works, and how to use it. The deep math lives on First Principles.

Overview discover → route → check → observe

Hydra picks the model best suited to each task, and can check the answer before you rely on it. It discovers every model you can reach (hosted APIs, local servers, CLI agents), routes each request to a model measured capable at that task type (today the lowest-cost one that clears the bar, with stronger models as the fallback chain), checks the answer with verifiers when you ask it to, and logs every request. No single vendor is privileged.

Pure Go, single static binary.

Usage
# Homebrew (recommended)
brew trust ankit373/hydra && brew install ankit373/hydra/hyctl

# npm  ·  or run once, no install:  npx hyctl
npm install -g hyctl

# pip
pip install hyctl

# Standalone installer, macOS and Linux
curl -fsSL https://raw.githubusercontent.com/ankit373/hydra/main/install.sh | sh

# Standalone installer, Windows (PowerShell)
irm https://raw.githubusercontent.com/ankit373/hydra/main/install.ps1 | iex

# From source (Go 1.26+)
git clone https://github.com/ankit373/hydra.git && cd hydra
go build -o hyctl ./cmd/hydra
Checksums

Both installers, and the npm and pip packages, check the download against the release's checksums.txt. They refuse to install if that file cannot be fetched, does not list the archive, or does not match, or if no sha256 tool is found. HYDRA_INSECURE=1 skips the check. Pin a version with HYDRA_VERSION and change the directory with HYDRA_BIN ($env: on PowerShell). On Windows the script installs per user to %LOCALAPPDATA%\Programs\hyctl and adds it to your user PATH, with no administrator rights. Prebuilt archives are on the releases page.

Platforms

Every release builds hyctl for macOS, Linux and Windows, each on x86-64 and ARM64. The README's platform table is checked against the build matrix by a test. Windows has no Homebrew, so use npm, pip, install.ps1 or the archive.

Not to be confused with the unrelated hydra and hydra-cli npm packages, or homebrew-core's hydra (a password cracker). This project's CLI is hyctl.

Command reference every command on one page

Every hyctl command, grouped by what it is for. The sections below explain the main ones in depth. hyctl <command> --help lists every flag.

All commands

hyctl init                              # first-run wizard
hyctl probe                             # scan and display all available models
hyctl status                            # live state: models that can run, budget bars, burn-rate risk
hyctl tui                               # interactive cockpit, six views, ? for shortcuts
hyctl version                           # version, commit, build info
hyctl upgrade                           # self-update, checksum-verified (curl installs only; brew installs: brew upgrade hyctl)

# Model registry (add a new model at runtime: no rebuild)
hyctl models list                       # known models, marked with what can actually route now
hyctl models add kimi-k3 --provider moonshot --cap-score 85   # record a score (not a model it can run)
hyctl models remove kimi-k3             # remove one of your additions
hyctl models sync                       # import the OpenRouter catalog (provisional scores)

# Dispatch
hyctl dispatch "..."           # route a prompt to the best model
hyctl dispatch --dry-run "..." # preview routing without executing
hyctl dispatch --kind summary "..."  # rank models on their record for this kind of work
hyctl dispatch --local "..."   # local models only, no API calls
hyctl dispatch --swarm --swarm-mode best "..."   # fan out to many models, judge best
hyctl dispatch --confidence 0.95 "..."  # SPRT: ask until its estimate clears this target
hyctl dispatch --check ground "..."     # check the answer against the context the prompt fenced
hyctl dispatch --check links "what did the regulator decide? cite your sources"   # each link must resolve and hold the quote; only the URL is sent
hyctl dispatch --check citations "list the key papers on retrieval-augmented generation"   # every DOI and arXiv id must exist and match its quoted title
hyctl dispatch --check match:labels=labels.txt "label this ticket: ..."   # the answer must be one of the labels
hyctl dispatch --check 'sum:total=items[].amount' "pull the line amounts and total from this receipt as JSON"   # the lines must add up to the total
hyctl dispatch --check 'cmd:check-jsonschema --schemafile invoice.json {file}' "pull the invoice fields as JSON"
hyctl dispatch --kind classification --check gen "is this ticket billing, bug or how-to? ..."   # checks written for the request by another model
hyctl dispatch --kind extraction --check gen:fields "pull vendor, total and date as JSON: ..."   # a verdict on every field, each broken one listed
hyctl dispatch --check ground --require-pass "..."   # exit 0 passed, 1 a check failed, 2 a check could not run
hyctl dispatch --kind writing.support --source-only "reply to this customer: ... <fenced policy>"   # only what the docs say, or "the documents given do not cover this"
hyctl dispatch --schema invoice.schema.json "pull the invoice fields as JSON: ..."   # check every field the schema lists, no extra model call; a string that breaks its pattern or format is marked bad_format
hyctl dispatch --schema tax-form.schema.json --max-fields 30 "pull every box from this form as JSON: ..."   # 90 fields: three calls, one merged object, checked field by field

hyctl vet --confidence 0.9              # sample each file with as many models as its blast radius warrants
hyctl vet --json                        # exits 3 on a blocking finding, so a script can gate on it
The eval corpus stays on your machine

The corpus behind hyctl eval is the one thing Hydra keeps word for word and for good, because it is the only data a router can be improved against. It is your own prompts, documents and code, so it stays in ~/.hydra/evalset/, nothing that prunes logs can reach it, and there is no upload path. A test enforces that: no Hydra package that can reach the corpus imports anything able to open a socket or run a program, and the third-party packages it rests on are pinned by name, so a new dependency is a decision rather than a side effect.

How it works

Chat executes: the route line names the routing level, model and strategy the router picked and why, then the proof strip reports what the run planned, edited and verified. An empty chat lists four starter tasks across kinds of work, and 1-4 fills one in. shift+tab cycles the modes: Ask, the default, which answers and never writes, then Edit, Plan and Auto (plan → edit → run your tests → fix → repeat), and ctrl+o overrides where the next task runs without changing what it does. Models is the discovered estate by provider, each model at its routing level, with a server's children greyed when the server itself is down. A model whose record at a kind of work got worse says so in its detail, with the day and how many it got right since, and says when it is back to normal. An empty chat also names up to three models that got worse or came back this week. Audit carries the calibration scorecard, the hash-chained log's integrity, the guardrails actually in force, and anything waiting on a human. Agents, Activity and Usage cover work in flight, per-run traces, and where the money went. Usage also shows what each passed answer cost over the last 30 days, with its pass rate and a 95% interval, beside the best single model on your own record for the same kind of work; until 30 answers have been checked it says so and shows no figure. ? lists every key, rendered from the keymap itself so it cannot drift.

Streaming

An answer appears as it arrives rather than all at once when the task finishes, so a slow model and a stuck one no longer look the same. The frame repaints five times a second, which is also what coalesces the stream: deltas land every ~20ms and the render never runs per delta.

When a model gives up part-way through, its partial output collapses to one dim line naming the model and the reason, so it cannot be mistaken for the answer, and e expands it again. The text is kept, not re-fetched. Only plain routing streams: a swarm has several models answering at once and consensus picks by judge after N replies, so neither has a single stream to show.

Modes

A mode sets what a task does. shift+tab cycles the basic ones and m opens the full picker.

ModeWhat it does
AskThe default. Answers only and never writes files. shift+tab reaches Auto when a task should change one.
EditA direct change when the prompt names an existing file (validated, rollback-safe, snapshotted). Otherwise it answers and says so.
PlanDrafts numbered steps on a low-cost routing level and waits. enter or y runs them, esc discards them.
AutoPlan, edit, then check: runs go test ./... (or your workspace.yaml validator) through the oracle, feeds failures back for up to 2 fixes, and shows a proof strip: plan ✓ · edit ✓ file +A/−R · tests ✓/✗.
ArchitectAuto, but plans on a strong routing level and does the work on a low-cost one.
CarefulAuto, but every file write needs a y/n before it lands.
UnattendedAuto with no confirms and a hard $0.50 cost cap per task. It stops, visibly, at the cap.

Where a task runs is separate: ctrl+o overrides the next task's routing (auto, force a routing level, local only, best of 3, or a consensus check at 90-99.9%). After an edit, /diff shows the diff, /undo restores the snapshot taken before the task (it asks first), and /open opens the file. These are typed commands, not bare letters, so a message that starts with x or a is just text. The code panel appears once a task streams a file or a diff; until then the chat takes the full width.

Parallel threads

Chat runs several tasks at once.

KeyWhat it does
ctrl+tNew thread. A chip strip under the header shows each one: ⠸ running, ● needs you, ✓ done, ◱ queued.
alt+1-9Jump to that thread. ctrl+←/→ cycles them, and the input bar names its target (→ thread 2).
ctrl+\Split: pin a second thread beside the active one (needs 100 columns or more). Each side scrolls on its own.
ctrl+bSend the thread to the agents view. It keeps running and pings chat when it finishes or needs you.
ctrl+gJump to the next thread that needs input (a plan waiting, a confirm, a failure).
/apply, /undoApply an isolated thread's worktree back to your tree, or discard it (asks first, since it deletes the thread's edits).
ctrl+sSelect mode: hand the mouse back to the terminal so you can select and copy text. Press again for wheel scrolling.

Isolation. Read-only work shares your checkout. Each thread that can edit gets its own git worktree (~/.hydra/worktrees/tN-…, branch hydra/task-tN-…) cut from your repo. /apply merges it back with plain git: a clean apply stages the diff, a divergence leaves normal conflict markers and keeps the branch, and unsaved edits of your own to a file the thread touched block the merge before it starts, so nothing half-lands. Two threads editing the same (or graph-coupled) files never race: the second queues (◱ queued behind 1 · both touch <path>) and starts when the first is applied or discarded. Outside a git repo the TUI says so and runs edits one at a time, in place. Worktrees left by a crash are listed at startup and never deleted for you.

Terminal notes: alt+1-9 needs the option key to send ESC (iTerm2: "Esc+"; Terminal.app: "Use Option as Meta key"), and ctrl+b is tmux's default prefix, so rebind tmux or press ctrl+b ctrl+b.

What you see is measured

Every figure comes from the machine's real logs. One that cannot be computed shows —, never an invented number. Lists, overlays and the audit view all scroll (j/k, arrows, page keys, mouse wheel). Colours follow light and dark terminals (force one with HYDRA_THEME=light|dark), body text uses your terminal's own foreground, and under NO_COLOR the active tab still reads [chat]. Log output from background work goes to ~/.hydra/logs/tui.log while the TUI owns the screen.

hyctl dispatch the router

Sends a request to a model measured capable at its task type, with automatic fallback. Today that is the lowest-cost model that clears the bar. The core command.

How it works

1 · classify → enum/routing level · 2 · policy gate (PII can block before any network call) · 3 · select highest-CapScore available model at/under routing level · 4 · execute · 5 · on failure fall down the chain to local Qwen · 6 · log tokens + cost. ~1.1µs of decision overhead.

When the model that answered got worse at this kind of work in the last 14 days, or came back, one dim line under the route line says so: summary record for <model> changed on 12 Nov. A model passed over because of its record since a drop is named on the same line. Nothing is printed when nothing changed.

Good enough

Hydra counts a model as good enough at a task type only when it is still good enough after allowing for luck. A model that got 22 of 24 answers right may just have had a good run, and when several models are held to one bar, the one whose average clears it is often only the luckiest. So the bar is checked against the lowest rate the model’s record supports at 95%, not against its average. 95% is the level --confidence uses by default. --dry-run prints both numbers, for example an average of 91 and at least 82 at 95%.

Routing reads the record since the last detected change, not the full history. A model that got worse stops clearing the bar within tens of answers, since it needs 20 judged answers since the change before it counts as measured again, and the work goes to another model that does clear it. When none does, the order is the plain ranking again, which is how a demoted model gets asked again.

Checking one answer

--check judges one answer. It does not combine with --swarm or --confidence, and each verdict goes to the eval corpus under the request's kind. ground checks the answer against the source the prompt fenced, match:labels=<file> against an allowed label set, and cmd:<command> runs any command that exits 0 on a good answer. gen has another model write checks for the request's kind: a yes/no rubric for writing, sentence-by-sentence support for a summary, fields, source values and any total the model says should add up for an extraction (add gen:roundtrip for a second model's extraction to compare; with both, each field prints once, marked as in the source, agreed by the second model, both, or what failed), and the label set the request names for classification. For code, gen:tests=<file> names the file the answer replaces: another model writes a few unit tests and one property test for it, and they run on a copy of the module, before and after the change, with the network off (see offline runner). A test that fails both times is more likely wrong than the answer, so it is dropped and counted in the detail. Go only for now; another language, no file, or no way to cut the network is not checked. Your working tree is never written.

When a check really fails, the request reruns once on a model measured stronger at that kind of work, sent the rejected answer and the error; a check that could not run never reruns. With --tier or --enum the first answer still comes from that tier, and the rerun may go to a stronger model outside it. Both answers are filed under the model that wrote them. --max-escalations sets how many reruns (default from max_retries and escalate_on_fail in policy.yaml, 0 turns it off), and --max-cost covers the rerun too.

Prompt caching

On by default for every request, whatever the kind of work. prompt_cache: true in registry/policy.yaml asks providers that cache only when asked, such as Anthropic, to cache the system prompt and tool list, so a repeated start is billed at the cache read rate. OpenAI, Gemini and DeepSeek cache on their own. A policy rule that sets prompt_cache: false turns it off for the work it matches.

Streaming

On a terminal the answer is drawn as it arrives: a spinner covers the wait before the first token, then tokens append, then the token counts, elapsed time and measured TTFT print as a footer, since none of those numbers exist until the call returns. Measured on a local 7B: 435 deltas spread over 9.9s of a 10.0s call, where before there was nothing on screen for the whole ten seconds.

Piped output never streams and is byte-identical to before, so scripts are unaffected; --no-stream asks for the same buffered rendering on a terminal. When a model fails part-way through, its partial is collapsed off the screen and replaced by one line naming the model and the reason, because a partial left on screen reads as part of the answer. Nothing is erased once it has scrolled past the top of the window.

Seven executor paths stream natively: the OpenAI-compatible wire shape (and Azure, which shares it), Anthropic, Gemini, Cohere, Bedrock over its binary event stream, Ollama, and the agy CLI. Replicate does not, because its prediction API polls. A model that cannot stream is not a second code path: it delivers its whole output as one piece, so each surface is written once and the two kinds cannot drift apart. A collapsed partial reads like this, and the trace command is offered only when payload capture is on, since without it the span stores no text:

⤺ abandoned  openrouter/gpt after ~212 chars: 429 rate limited
    hyctl trace view run-7f2a --span 9c1d4e02

A fan-out has no single stream to show, so --swarm and --confidence draw a live panel instead: every model that was selected, with its state, elapsed time, tokens and the cost as it accrues. A confidence run adds the running log-odds against the threshold it has to cross, so an ensemble that stops after two models says why it stopped. The panel is erased when the run ends, and the result printed after it is unchanged.

dispatch --confidence ask until the estimate clears a target

Ask models adaptively until Hydra's estimate that the answer is correct clears your target, then stop. The estimate is only as good as the calibration behind it, so it is not a guarantee. A mode that accepts only under a stated error bound is planned in #1549.

How it works

Instead of always asking a fixed number of models, an SPRT (sequential probability ratio test) asks them one at a time, in most-evidence-per-dollar order, adds up the calibrated log-likelihood ratio of their votes, and stops as soon as it crosses the boundary your target implies. --file raises the bar by blast radius.

Usage
hyctl dispatch --confidence 0.95 "does this contract let either side cancel early? quote the clause"
hyctl dispatch --confidence 0.95 "is this migration safe for prod?"
Calibration comes first

An uncalibrated source has sensitivity = specificity = 0.5, so its vote adds ln(0.5/0.5) = 0 however firmly it agrees. With no calibrated source for the task type the estimate cannot move, so Hydra refuses the run rather than ask every model and arrive back at 50%, and tells you what does carry evidence:

$ hyctl dispatch --confidence 0.9 --kind writing.support "draft a reply to this refund request: ..."
Error: no head this run would sample has been scored in domain "writing.support", so
--confidence would sample every head, move the estimate nowhere and hand back 50%.
A source only carries evidence once its verdicts have been scored against outcomes.

  Other domains with evidence: trust-bench-v2
  Record an outcome:     hyctl trust record --source <head-id> --domain writing.support --said-correct --outcome correct

When some source has scored the task type but this run would not ask it, the error names that source instead. The two cases need different fixes. Each model and check earns a measured sensitivity, specificity and diagnostic power D: a coin-flip source (D≈0) adds nothing, and a proven one lets a single vote go a long way.

Recording only your own answers is not enough. A model that produced an answer always "said correct", which leaves specificity unmeasured, so a single vote stays under ln 2 = 0.693 nats against the 2.944 a 95% target needs. The models that disagreed are what fix it: hyctl trust outcome replays a past run's ledger once its answer is known, so a model that dissented from an answer that turned out wrong earns the true negative specificity comes from.

Every confidence run ends by printing its task_hash and the hyctl trust explain command for it. hyctl trust stats says outright when achieved confidence never left the 50% prior, which means the runs paid for models without learning anything.

For code: a higher bar on risky files

Point Hydra at a dependency graph (graph.json from Graphify or any tree-sitter indexer) and the bar scales with how much code an edit could break. A fix to a file everything imports needs far more certainty than a fix to a leaf helper:

hyctl graph blast internal/auth/token.go        # 3 transitive dependents → demands 96.7%
hyctl dispatch --confidence 0.90 --file internal/auth/token.go "rotate the signing key"
#   graph: blast radius 3.00 → demands confidence ≥ 96.7%  (raises the 0.90 floor)

In synthetic benchmarks this cuts model calls by about 49% on easy tasks and 24% on a mixed workload at 98% accuracy or better, while asking more models than a fixed swarm on hard tasks, which a fixed-size ensemble cannot do.

How it works

It streams as server-sent events and passes tool calls through on every dialect it speaks. X-Hydra-Task-Class routes on that class (and turns on temperature), and X-Hydra-Max-Cost-USD can only lower the ceiling. policy.yaml's max_cost_usd caps every request, with or without that header. X-Hydra-Redact: on sends a hosted model placeholders for detected values and restores them in the reply, streamed or not; X-Hydra-Redacted says how many values were replaced. A placeholder split across two stream chunks is held back until it can be restored, so the client never sees half of one.

Each request is its own run, and the run records which chat it continues: a key hashed from the system message and the first user message, which a client resends unchanged every turn. A client whose opening changes between turns can name the chat with X-Hydra-Conversation (up to 128 bytes) instead.

A class with [[serve.verifiers]] in config.toml (class, kind = "match", id, then a labels file or a pattern) has each buffered answer on an objective route checked, and escalates to a model measured better in that class, at most --max-escalations times (default 2). In hyctl trace view the rejected answer is scored check=0 with the reason, and the next attempt reads "escalated from <span>".

A request can name its own checks with X-Hydra-Check, one per header line: ground, match:pattern=<re> or gen. Anything else is a 400 that lists these. ground and match join the escalation above the way a configured verifier does; gen needs X-Hydra-Task-Class and runs after the answer. The reply says X-Hydra-Check-Result: passed, failed or not_checked, with X-Hydra-Check-Detail saying why, and the same under hydra in the body. A check that could not run is not_checked, never passed. Streamed and tool-calling requests are checked after the answer and never retried; a stream carries the verdict in its final chunk's hydra field.

With [idle] enabled = true the server compacts quiet conversations on a local model (hyctl idle status) and, by default, sends a checked pack in place of the turns it covers only once the provider's prompt cache has expired. swap = "off" never does, and "auto" also does it while the cache is warm when the cache rates say the rewrite pays back. Any change to the covered turns sends the request as it came. A request that used a pack says so: X-Hydra-Compacted: <pack>; probes 9/10, and the same under hydra in the body; its answer is not cached.

Requests must name the bound address as Host (127.0.0.1, localhost or [::1] on a loopback bind), carry no Origin unless --allow-origin lists it, and POST with Content-Type: application/json. Over --max-inflight (8) or --rate (120 a minute) a request gets 429 with Retry-After, which SDKs retry.

hyctl trust calibration and verification

Builds and inspects the calibration behind --confidence. Each source earns a measured reliability from real outcomes.

How it works

A Beta-Bernoulli posterior over sensitivity/specificity → a per-vote LLR and a diagnostic power D (KL divergence, nats). A coin-flip source has D≈0 and is ignored. The defect-cost model prices a wrong answer and sets the required confidence.

Each source’s record in each kind of work is also watched for a change: when a model or a check gets worse, the table shows when that was found and its record since, and when it gets back to its old rate, the day it recovered. A short run of misses at a steady rate is not called a change, and one called by mistake is taken back once the source is right again. A model nobody is calling is not assumed broken for ever; while others are judged on the same kind of work its old record slowly stops counting, so a fixed model starts again on a fresh record. Routing reads that record since the change, so a model that got worse stops getting the work within tens of answers.

Measured in simulation, with 1,000 runs per case after 1,000 answers at a steady rate: a drop from 90% to 74% right is found after a median 89 answers (175 at the 90th percentile, 6% not found within 200). Smaller drops, or the same drop from a 60% base, are usually not found within 200. On a steady rate it raises about 0.03 false alarms a month at 1,000 answers a month, and fewer at lower traffic. It is tuned to be quiet rather than fast.

Checks that fail together

Every verdict on an answer, from tests, a linter, a grounding check, a model vote or a person, is kept in one log. hyctl trust joint takes the answers that later turned out wrong and reports, per kind of work, how often each pair of checks passed the same one, next to the rate you would expect if they failed independently. A pair well above that rate is one check, not two. Below 20 shared wrong answers no rate is shown, because the 95% bound would be wider than the rate. Each check’s rate is also watched for a change, such as a judge model swapped underneath, and a changed check shows when and its rate since.

Certified or not verified

hyctl dispatch --certify 0.05 marks the answer one of three ways: certified under independence (its checks’ evidence multiplied, after checks that fail together are counted once), certified under any dependence (a joint pass pattern), or not verified, with the reason: too few labelled wrong answers, no way to reach the bar, the budget, or no check for this kind of work. Today it looks at one answer, judged by the request’s --check verdicts, and never reruns; the label and the numbers behind it go on the answer’s span as a certified score, and the exit code is 0 either way. Grounded answers and writing will mostly print not verified until their checks get much stronger. What alpha bounds is the chance of accepting a wrong answer, per task. It is never the chance that an accepted answer is wrong, which it does not bound.

hyctl compare two models on your own kind of work

Puts two models side by side for one kind of work, read from your own checked answers. It calls no model, unless you ask it to rerun tasks with --replay.

How it reads

For each model: how many of its answers were checked, how many passed, and the 95% lower bound on its pass rate (Wilson). If its record changed, the row also shows the record since that day. One model is called ahead only when its lower bound is above the other’s upper bound, judged on the record since any change. Otherwise it says there is no clear difference yet, and roughly how many more checked answers each would need if the rates hold. Cost per checked answer shows as unknown for now, rather than a guess.

A fair sample: replay

The record only holds what each model happened to be given. --replay N sends up to N of the newest stored tasks of the kind to both models and runs each task's check again, so both answer the same tasks. It can rebuild ground and the generated checks whose spec is stored; other tasks are skipped and counted. It prints the worst-case cost and asks before spending unless you pass --yes, and it stops before a task that could take the spend past --max-cost. The answers are filed, so the replay adds to the record, and it prints the same table for that sample.

hyctl idle compact while quiet, check before use

Shrinks a long conversation on a local model while you are away, and only uses the result once it has passed its checks.

What it does

When a conversation has gone quiet and the machine is free (on AC power, low load, memory to spare), Hydra writes a pack on a local model: the goal, the rules copied word for word, decisions with their reasons, and a pointer back to every original turn. Nothing is deleted. A new request in any conversation stops the job at once.

What has to pass first

The pack must be smaller than the turns it covers, every pointer must resolve, the rules must match the originals byte for byte, and it must state no number, name, date or quote the originals lack. Then the same questions are put to the local model twice, once with the full turns and once with the pack, and at least 0.8 of the answers must agree: paths and numbers exactly, other answers by word overlap. The model that wrote the pack also answers, so agreement is weaker evidence than a second opinion. A conversation too big for the model's window is checked in parts and marked partial, and a partial pack is never used automatically. A pack that fails is kept beside the others with the reason and is never used.

When it is used

Off by default. With [idle] enabled = true in config.toml, hyctl serve checks once a minute. The pack is sent in place of the turns it covers only when the provider's prompt cache for the old conversation has expired (swap = "cold_only", the default), because rewriting a warm cache costs more than it saves. swap = "auto" also does it while the cache is warm when the cache rates say the rewrite pays back, and "off" never does. Any change to the covered turns sends the request as it came. A request that used a pack says so in X-Hydra-Compacted, and its answer is not cached. It never calls a paid model, and every original stays in the payload store.

See it, undo it
hyctl idle run                          # one tick by hand
hyctl idle status                       # each conversation and the last reason one was refused
hyctl context packs                     # staged packs: turns covered, probes agreed, tokens, uses
hyctl context show-pack <id>           # the rules and state the model is sent
hyctl context restore <conversation>   # its next request goes out as it came; no new packs for it
Needs

Payload capture on (capture_payloads = true), so the original turns are stored, and a local model that is up. With either missing, hyctl idle status says so and nothing is compacted.

A rule narrows by agent, resource, action, or any mix. The first match wins, so put specific rules above general ones:

{
  "default": "allow",
  "rules": [
    {"agent": "hydra-swarm", "resource": "registry/**", "action": "write",

     "decision": "ask"},
    {"classification": "mcp-quarantined", "decision": "deny"}

}

deny refuses and records it. ask parks the task under hyctl ask, which is the right verdict when you want a person in the loop rather than a refusal: dispatch stops before anything runs and never falls through to a lower-cost model. hyctl mcp check exits 3 on a deny and 4 on an ask, so a script can tell a refusal from a question, and 0 only ever means allowed. hyctl mcp registry safety score for the MCP servers on your machine

Every existing MCP directory answers "does this server exist", none answer "is it safe to run with my credentials right now," and star/download counts are actively misleading (the most-starred servers score worst on quality in independent research). This scores what's actually installed instead of indexing everything that exists.

Subcommands
hyctl mcp registry sync             # pull the official MCP registry into a local cache
hyctl mcp registry scan             # list servers installed across Claude Code/Desktop, Cursor, Windsurf, VS Code
hyctl mcp registry audit            # resolve + score installed servers, update lifecycle state
hyctl mcp registry export --out DIR  # static index.html/index.json of audited servers
hyctl mcp registry backtest         # validate scoring against known real incidents (postmark-mcp, CVE-2025-6514)
hyctl mcp registry list             # audited servers by safety score
hyctl mcp registry clear <server>   # recover a server quarantined in error

Scoring is shaped around the CSA MCP Selection Scorecard's four categories (Security Implementation, Repository Health, Operational Security, Community & Governance), automating a taxonomy the MCP Security Working Group already endorsed, not inventing a new one. Only a confirmed finding (a known advisory match) quarantines a server; a name-similarity heuristic lowers the score without condemning it, because quarantine has no automatic way out, clear is the manual recovery path. A category nothing could be checked in contributes a neutral baseline rather than being dropped from the average, so failing to reach GitHub can never raise a score, and a server nothing is known about reads "insufficient evidence" rather than a number. A server's status (new → provisional → trusted → flagged → quarantined) drops back to provisional on every version bump, detected via a content-hash diff of the manifest, the direct fix for the postmark-mcp rug-pull pattern (15 clean npm versions, then a malicious one). scan never reads env-var or secret values from client configs, only server identity.

A server can keep its version and rewrite what its tools say, so each tool's name, description and input schema is hashed too, and any change sends it back to provisional, with the before and after printed by audit. Descriptions are also checked for text written for the model rather than the user (directions about other tools, requests to read files or send data, hidden characters, padding), each reported with its exact span and never quarantining on its own. Both need the server's tools/list result saved at $HYDRA_HOME/mcp_tools/<server>.json: audit never starts a server to ask, and says "not checked" for any server without one.

Feeds back into the ledger: hyctl mcp check auto-classifies a tool call as mcp-unverified, mcp-flagged, or mcp-quarantined from a server's registry state, the same way PII is auto-detected from content, so a policy rule can gate on it automatically. Below that: mcp-behavior-change, a server whose ledger history has only ever shown one kind of access (read, say) suddenly performing another (network) is flagged from local history alone, no registry data or CVE required. A server's first-ever call is never flagged, there's nothing yet to compare it against.

The exported page (export) carries a disclaimer, this is a probabilistic signal from automated checks, not a guarantee of safety or a claim about a publisher's intent, and every row links a pre-filled dispute issue against this repo, since a public negative signal about a real project needs a correction path before it ships, not as an afterthought.

Grounding

hyctl oracle ground checks a summary you already have against the source it came from: every number, date, name of a person or company, path, identifier and quoted phrase of three or more words has to appear in it. Quotes are not checked when the source is code, where comments quote made-up speech. PII / local-only enforced, not conventional

With local-only policy on, any prompt containing sensitive data is blocked from leaving your machine at the dispatch layer, before any network call.

Detected

Social Security numbers, credit cards, phone numbers, IBANs, email addresses, IP addresses and private-key material. Secrets: key = value pairs whose name says password, secret, token or API key, in JSON ("api_key": "…") and env files (OPENAI_API_KEY=…) too, plus AWS, GitHub (classic and fine-grained), GitLab, Slack (tokens and webhooks), Stripe, npm, Hugging Face, Groq, OpenAI and Google keys, a bare 40-character AWS secret key, JWTs and authorization headers. Turn it on in hyctl init, and a matching prompt goes to a local model:

$ hyctl dispatch "process payment for card 4111-1111-1111-1111"

  Policy violation: prompt contains PII (credit card pattern)
  Action: routing to local-only head

  Dispatching → ollama/qwen3:8b  [local, no API call made]
What this is not

Detection is a denylist over the prompt text, so it can only stop what somebody wrote a pattern for. The same patterns redact the opt-in payload, cache, embedding and retrieval stores before anything is written. They do not cover names, street addresses, a password with no name next to it, a secret split across lines or encoded, or a vendor format not in the list. That is why the egress gate classifies by path instead, and why hyctl security withholds its coverage score while the access policy still defaults to allow.

Coverage is measured, not claimed. Against the presidio-research synthetic set, some detector fires on 18.7% of the 1,387 texts that carry PII: 100% of emails, SSNs and IBANs, 93% of cards and IP addresses, and 69% of phone numbers. The gap is names, street addresses and organisations, 1,509 spans with no pattern to write, which is what a trained NER model is for. Phone numbers are recognised by a country code, a bracketed area code, the 3-3-4 grouping or a leading trunk zero; a bare run of digits is refused for the same reason nine bare digits are not read as an SSN. Re-run the figures with go test ./internal/policy -run TestPII_Recall -v.

hyctl policy ner --head <id> measures whether a model can read the half no pattern reaches. It asks 470 labelled texts and reports recall and false positives apart, because each alone is easy to pass. On one machine a 7B scored 0.87 recall at 0.00 false positives, while a 0.5B scored 0.86 recall and said yes to 94% of the negatives. Both are judged on the 95% interval, so a model is eligible only when the sample is large enough to say so. Decoding is pinned greedy, and an answer that is neither yes nor no is counted apart, never read as a no. The report is saved per model, and it is the only thing that lets --redact=names ask a local model to mark names: one that has not passed here is never asked.

Redact instead

Local-only keeps the whole request on your machine, so a stronger hosted model never works on it. --redact sends the hosted model numbered placeholders instead, and puts the real values back into the answer on your machine:

$ hyctl dispatch --redact "draft a reply to sam.lee@example.com about the late refund"

  # the hosted model sees: draft a reply to <<EMAIL_1>> about the late refund
  Hi, I have passed your refund to finance. We will write to sam.lee@example.com by Friday.

  redacted: mistral-large saw 1 value(s) as placeholders; the answer above has them restored

A local model gets the original text. The map from placeholder to value stays in memory and is never sent or written. A value keeps its placeholder across fallbacks and reruns, and the answer is restored before any check reads it. When the hosted answer needed a real value, say whether an IBAN is German, the request reruns on a local model with the original text; with no local model, the answer says which placeholder it could not use. Set [policies.pii] action = "redact" to do this for every prompt with PII. A file the egress gate calls secret still goes only to a local model. It runs on a single dispatch, not with --swarm or a confidence run, and the answer prints once restored rather than streaming.

--redact=names (or action = "redact-names") also covers what no pattern finds. A local model that hyctl policy ner measured eligible on this machine lists the names and street addresses in the request, and each becomes <<PERSONAL_1>>. With no eligible local model the pass is skipped and the receipt says so. If the pass fails or takes longer than two minutes, nothing is sent.

Measured in CI on a made-up corpus of support, HR, finance, log and legal texts: no detected value reached the hosted model, and every planted email, phone number, IBAN, card, SSN, IP address, AWS key id and credential was replaced. Names and street addresses were not, 0 of 7, because no pattern covers them. Re-run with go test ./internal/dispatch -run TestRedaction_NoDetectedValueReachesRemote -v.

Egress gate secrets by where they live

The egress gate classifies a file by where it is, not what is inside it, so a whole category is closed whether or not the contents look like anything.

How it works
$ hyctl edit --file "$PWD/deploy/.env" --enum SIMPLE --prompt "rotate the database password"

  🔒 secret content (deploy/.env), routing to a local head only
  Dispatching → ollama/qwen3:8b  [local, nothing left this machine]

With no local model running, the default refuses rather than fall back to one that reaches the network:

no dispatchable heads: content classified secret (deploy/.env) and no local head
is routable. Start one (`ollama serve`), or set egress.strict = false in
config.toml to allow it out

The rules live in registry/sensitivity.yaml, built into the binary and overridable at $HYDRA_HOME/registry/sensitivity.yaml. They cover env files, private keys, cloud and cluster credentials, tfstate, SSH and package-manager config, and ~/.hydra itself, with an allow list so a committed .env.example is not treated as a secret. Turn the floor off with:

[egress]
  strict = false   # default true; a config with no [egress] section is strict
What it guarantees

No file matching a rule reaches a model that leaves the machine, errors deny rather than allow, and a payload that declares no origin is refused, so a new code path that forgets the gate breaks loudly instead of leaking quietly. Every decision is recorded in the ledger with the rule that made it.

Where the boundary is. CLI agents have their own file access. Hydra guarantees what it sends; it cannot control what agy or codex decides to read once handed a task. The guarantee is total only when the work runs on a local model, which is exactly what the gate reroutes to.

The lethal trifecta

Every request writes where its payload came from to the ledger: what it was built from, how it classified, and whether the model it reached leaves the machine. hyctl security trifecta reads that:

  LETHAL TRIFECTA  2 dispatch(es) had all three legs and were not stopped
  over 7 dispatch(es) with recorded provenance

  private data         4 dispatch(es), read local files or environment
      deploy/.env                                  2
      internal/auth/token.go                       2
  untrusted content    4 dispatch(es), ingested content Hydra did not author
      head                                         4
  external comms       6 dispatch(es), reached a head that leaves the machine
      openai/gpt-5                                 5

Any one of the three is fine; all three at once is what turns a poisoned input into a data leak with no software bug involved. The headline is exposure, not presence: a trifecta the gate refused is reported as contained, because a dashboard that flags a working control teaches people to ignore it.

Receipt

hyctl egress receipt [run-id] says, for each model a run asked: its provider, whether it was local or remote, how sensitive the request was, and how many values of each kind it saw as placeholders and got back restored. It defaults to the last run, takes --json, and says whether the ledger's hash chain still verifies. It holds counts, never a value or a hash of one.

$ hyctl egress receipt

  egress receipt run 20261116-a1b2
  litellm/claude-sonnet  remote  provider litellm  internal  allow
    sent as placeholders: CREDIT_CARD 1, EMAIL 2   restored: 3

  ledger chain: verified

Least-privilege agents each subprocess gets only its own key

An agent subprocess gets a base set of variables (PATH, HOME, locale, proxy), its own provider's credential and its own tool configuration. Nothing else crosses, so a CLI agent no longer holds your cloud keys, every other provider's API key and SSH_AUTH_SOCK for the length of a call.

Models

The allowlist cannot be complete, since every CLI agent reads its own settings and they change. If a model needs a variable Hydra does not know about:

export HYDRA_HEAD_ENV=SOME_AGENT_TOKEN,SOME_OTHER_VAR

Model subprocesses are also bounded, so a grandchild holding the pipe open cannot hang a call on a process that already exited. Local model weights are fingerprinted by digest alongside agent binaries, so a swapped model behind a familiar name is caught the same way a replaced agent binary is, which matters because Ollama pulls unsigned weights from a public registry.

Validators and checks

Validators, oracles, --check cmd: and hyverify run files a model may have just written, so they get the same base set plus toolchain paths (GOPATH, GOCACHE, GOFLAGS, NODE_PATH, npm_config_cache, VIRTUAL_ENV, CARGO_HOME, JAVA_HOME and a few more) and no credential at all. If a check needs another variable, name it in workspace.yaml:

validator_env: [PLAYWRIGHT_BROWSERS_PATH, DATABASE_URL_TEST]

A name that looks like a credential (it contains KEY, TOKEN, SECRET, PASSWORD, CREDENTIAL or AUTH, or starts with AWS_, AZURE_, ARM_, GOOGLE_, GCP_, GCLOUD_ or CLOUDSDK_) is refused, and hyctl security lists it. hyverify --env NAME,NAME does the same for one run.

Offline runner

Generated tests (--check gen:tests=<file>) run with no credentials, a CPU and wall-clock cap, and no network at all, loopback included:

Linux: a network namespace of its own, set up as your user through a user namespace. It has no interface that reaches the host or the internet.

macOS: sandbox-exec with a profile that denies network*, kept in the repo as internal/sandbox/offline.sb. DNS lookups fail too.

Anywhere else, or when the setup fails (Windows, a Linux with user namespaces turned off, Ubuntu 24.04's default AppArmor rule, a process that is already sandboxed): the code is not run, and the result is not checked: no network isolation, never a pass.

Offline runner             network off
  generated tests (--check gen:tests) run in a network namespace of its own, with no
  credentials and bounded CPU and time. They can still read and write your files

hyctl security --why shows which of these applies on your machine. On Ubuntu 24.04, sudo sysctl kernel.apparmor_restrict_unprivileged_userns=0 allows the Linux method.

Limits. Only the network is cut. The code can still read and write any file your user can. On Linux, a Unix socket with a path (the Docker socket, the system DNS resolver's socket) is not part of the network namespace, so it stays reachable. Apple marks sandbox-exec as deprecated, though it still ships and works.

Not included

Validators, oracles, --check cmd: and hyverify still run with your file and network access. Go's os/exec has no per-child resource limits, and faking them through a shell would re-split the arguments, which internal/oracle avoids on purpose. Filesystem containment needs a platform sandbox (sandbox-exec, bubblewrap or landlock), and none of them works the same on macOS, Linux and Windows, so it is tracked separately. What an agent may reach is set by the access policy.

A2A handoffs causal, conflict-aware

Work passed between agents carries a vector clock for causal ordering; concurrent handoffs touching overlapping files are flagged as conflicts. Saved to logs/last_handoff.json, replayed with --a2a.
